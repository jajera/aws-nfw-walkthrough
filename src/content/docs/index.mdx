## Why this lab

Dual-hub designs put a <Tooltip term="tgw" label="Transit Gateway" /> and
<Tooltip term="nfw" label="Network Firewall" /> in each Region. This walkthrough
drives the disposable Terraform lab
[`jajera/aws-nfw-lab`](https://github.com/jajera/aws-nfw-lab).

| Focus | What you prove |
| ----- | -------------- |
| Cross-Region | <Tooltip term="double-inspect" label="Double-inspect" /> — **both** hubs see the flow |
| Same-Region | One local NFW hairpin (e.g. Syd-dev ↔ Syd-prod) |
| Mesh first | TGW + spokes + peering, prove before NFW |
| Then NFW | Attach deny → allow; read flow logs to prove where |

What you build:

- Greenfield inspection + spoke VPCs (dev and prod) in Sydney and Auckland
- Demo hosts with HTTP and DNS; private zone `lab.demo`
- Hub-to-hub TGW peering; workloads attach only via RAM to their regional hub

## What you will do

<CardGrid>
  <Card title="Hubs" icon="rocket">
    Sydney → Auckland → Validate, then the same for Workloads.
  </Card>
  <Card title="Workloads" icon="seti:folder">
    Attach each spoke and demo host; validate both before peering.
  </Card>
  <Card title="Peer and prove" icon="approve-check">
    Hub peering, <code>lab.demo</code> DNS, then ping / curl / dig across Regions.
  </Card>
  <Card title="Prove where" icon="setting">
    Read flow logs to confirm cross-Region traffic hits <strong>both</strong> hubs.
  </Card>
</CardGrid>

| Expectation | Notes |
| ----------- | ----- |
| Own VPCs | Lab creates all four VPCs; nothing reused from the account |
| Cross-Region path | TGW peering; workloads never attach to the remote hub |
| Cost while running | TGW attachments + NFW endpoints + NAT (spokes) bill hourly |

<Aside type="caution">
  This lab costs money until you tear it down. Prefer 1 AZ and destroy when idle.
</Aside>
